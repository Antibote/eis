# EIS — техническое проектирование (Этап 1)

Engineering Intelligence System: анализ инженерной документации и оценка последствий
конструкторских изменений (гибрид: извлечение + граф знаний + формальные правила + RAG + LLM).

Статус документа: рабочий, обновляется по ходу разработки. Решения фиксируются в `docs/decisions.md`.

---

## 1. Анализ требований: что действительно определяет ценность

Мастер-документ описывает систему уровня промышленного PLM. За ограниченный срок её
целиком не сделать, поэтому разделяем требования на три группы.

**Ядро научно-технической ценности (без него проекта нет):**

1. Конвейер «документ → фрагмент → типизированная сущность» с неразрывной привязкой к источнику
   (документ, страница/лист, смещение в тексте, исходная строка).
2. Типизированный граф знаний, где у каждого ребра есть основание (evidence).
3. Анализ последствий изменения: обход графа с учётом типов рёбер, глубины и весов и
   **разделением классов влияния** (прямое / документальное / потенциальное / подтверждённое).
4. Формальная проверка ограничений (числа, диапазоны, единицы) — главный источник
   *надёжных* противоречий.
5. Эксперимент: 4 метода × одинаковые входы × эталонная разметка → P/R/F1, время, доля
   подтверждённых утверждений.

**Нужно для убедительной демонстрации:** веб-интерфейс (дашборд, библиотека, граф, анализ
изменения, противоречия, ассистент), экспорт отчёта, Docker Compose.

**Можно отложить без потери ценности:** см. раздел 8.

## 2. Архитектурные риски и меры

| # | Риск | Последствие | Мера |
|---|------|-------------|------|
| R1 | **Циркулярность оценки**: синтетические документы и экстрактор пишет один автор, поэтому экстрактор «подогнан» под шаблоны генератора | Завышенные метрики, критика комиссии | Генератор формулирует одно и то же требование несколькими вариантами (синонимы, порядок слов, разные записи чисел и единиц); часть формулировок не используется при разработке правил (hold-out); вносится шум (опечатки, OCR-скан, таблицы вместо текста). Эталон задаётся **моделью изделия**, а не результатами экстрактора. Ограничение явно описывается в работе |
| R2 | Нет GPU (CPU, 15 ГБ ОЗУ) | Локальная LLM медленная, большие модели недоступны | Ядро (извлечение, граф, правила, BM25, эмбеддинги) работает без LLM. LLM — опциональный слой (Ollama с 3–8B моделью или внешний API через абстрактный интерфейс). Эксперимент гибрида проводится в двух вариантах: с LLM и без |
| R3 | LLM «галлюцинирует» противоречия и факты | Нарушение главного принципа | LLM получает только пронумерованные фрагменты, обязана ссылаться на их ID; утверждения без валидной ссылки отбрасываются пост-проверкой (citation guard). Семантические противоречия от LLM получают статус «потенциальное», не «подтверждённое» |
| R4 | Транзитивный обход «заражает» весь граф | Recall → 1, precision → 0 | Затухание веса по пути, допустимые типы рёбер для каждого параметра изменения, порог, ограничение глубины; классы влияния вместо бинарного «затронут» |
| R5 | OCR (Tesseract) не установлен; качество OCR низкое | Сканы не обрабатываются | Tesseract ставится в Docker-образ; локально — graceful degradation с понятной ошибкой. В датасете 1–2 скана для измерения влияния качества документа |
| R6 | Разнобой единиц (°C/K, МПа/бар/кгс/см², мм/м) | Ложные противоречия | Модуль нормализации единиц с явной таблицей коэффициентов и тестами; при невозможности привести — статус «недостаточно информации» |
| R7 | Prompt injection в загружаемых документах | Компрометация ответов | Текст документов передаётся в LLM только как данные в разделителях, системная инструкция запрещает исполнять инструкции из них; детектор подозрительных фраз помечает фрагменты; внешний API выключен по умолчанию (`EIS_ALLOW_EXTERNAL_LLM=false`) |
| R8 | Переусложнение (Neo4j, очереди, микросервисы) | Не успеть к сроку | Модульный монолит: один FastAPI-процесс, сервисы — Python-пакеты с интерфейсами. Хранилище графа и векторов — за интерфейсами, реализации MVP в процессе |
| R9 | Синтетические данные выдаются за реальные | Репутационный риск | Каждый документ несёт пометку «СИНТЕТИЧЕСКИЙ ДОКУМЕНТ ДЛЯ ДЕМОНСТРАЦИИ»; поле `is_synthetic` в БД; в отчётах — явная оговорка |
| R10 | Неизвестна точная дата подачи на конкурс | Неверное планирование | План построен по неделям с приоритетами; конкурсный пакет можно собрать после этапа 5 из готовых артефактов |

## 3. MVP: минимально убедительный функционал

1. Загрузка PDF/DOCX/TXT/XLSX/CSV (+PNG/JPEG через OCR при наличии Tesseract).
2. Разбиение на фрагменты с сохранением страницы/листа и смещений.
3. Rule-based извлечение: требования (параметр, оператор, значение, единица, объект),
   компоненты (по обозначению из спецификации), материалы, испытания, ссылки на документы и НТД.
   Опционально — LLM-извлечение как второй проход, результаты которого сверяются с правилами.
4. Граф знаний (NetworkX), сохраняемый в БД (таблицы `nodes`, `edges`, `evidence`).
5. Анализ изменения требования → отчёт с классами влияния и обоснованиями.
6. Детектор противоречий: уровень 1 (формальный) и уровень 3 (графовый) — обязательно;
   уровень 2 (LLM) — при наличии модели.
7. Гибридный поиск (BM25 + эмбеддинги, слияние RRF) с фильтрами.
8. Ассистент: маршрутизация запроса (граф / поиск / анализ изменения) и ответ с цитатами;
   без LLM — экстрактивный ответ из фрагментов и графа.
9. Синтетический датасет «Насосный агрегат НА-200» + эталон + 5 сценариев изменений + 10 противоречий.
10. Экспериментальный стенд: 4 метода, метрики, таблицы и графики, воспроизводимый запуск одной командой.
11. Веб-интерфейс: 6 страниц, отчёт в DOCX/PDF.

## 6. Ключевые модели и алгоритмы (кратко)

### 6.1. Evidence — основа объяснимости
Каждая сущность и каждое ребро ссылается на одно или несколько `Evidence`:
`{document_id, page, bbox?, char_start, char_end, quote, method: rule|llm|table|graph_rule|manual, confidence, created_at}`.
Ребро без evidence создать нельзя (проверка на уровне построителя графа).

### 6.2. Требование
`TechnicalRequirement {id, code?, subject (компонент/изделие), parameter (нормализованный ключ:
temperature_max, pressure_nominal …), operator (<=, >=, =, range), value / low / high (в базовых
единицах СИ), unit_original, condition?, source evidence}`.

### 6.3. Анализ изменения
1. Найти требование `R`, вычислить дельту параметра.
2. Множество стартовых узлов: `R` и его субъект.
3. Взвешенный обход (модифицированный Dijkstra по произведению весов): вес пути = ∏ w(e) · decay^depth;
   веса задаются по типу ребра (CONTAINS вниз 0.9, USES_MATERIAL 0.8, DEPENDS_ON 0.7,
   DOCUMENTED_IN 1.0 — но класс «документальная связь», VERIFIED_BY 1.0 → «испытания»).
   Допустимые типы рёбер зависят от **физической природы параметра** (температура
   распространяется через материалы и сопряжённые детали, давление — через границу давления и т. д.).
4. Для каждого достигнутого компонента — повторная формальная проверка: совместимо ли его собственное
   ограничение (например, допустимая температура материала уплотнения) с новым значением.
   Нарушение → «подтверждённое техническое влияние» (с evidence обоих требований); путь есть, но
   проверка невозможна → «потенциальное влияние».
5. Документы: все `DOCUMENTED_IN` затронутых узлов → «требуют пересмотра»; испытания `VERIFIED_BY` → «требуют повторения».
6. Отчёт: для каждого вывода — класс, оценка достоверности, путь в графе, цитаты.

### 6.4. Противоречия
- **Формальные**: пары требований с одинаковыми (субъект, параметр) из разных источников →
  проверка пересечения допустимых интервалов после приведения единиц; несовпадение номинальных
  значений; нарушение иерархии (требование к узлу строже/мягче, чем к входящей детали в противоречивом направлении);
  материал с пределом ниже требуемого режима.
- **Графовые**: по цепочкам CONTAINS/USES_MATERIAL находятся ограничения, которые не
  встречаются в одной паре документов напрямую (косвенное противоречие).
- **Семантические (LLM)**: кандидаты — пары фрагментов с высоким семантическим сходством и
  одним субъектом; вердикт LLM с обязательными цитатами; статус максимум «потенциальное».
- Статусы: `confirmed` (формальное нарушение, обе стороны извлечены с уверенностью ≥ порога),
  `potential`, `insufficient_data`.

### 6.5. Оценка достоверности
`confidence(вывод) = f(уверенность извлечения сторон, тип evidence, длина и вес пути, согласие
независимых методов)`; формула фиксируется и калибруется на эталоне (reliability diagram) — это
отдельный пункт эксперимента.

## 7. Научная гипотеза и план эксперимента

**H1 (основная).** Гибридный метод (извлечение + типизированный граф + формальные правила (+ RAG/LLM))
даёт больший F1 определения затронутых компонентов и документов, чем (a) поиск по ключевым словам,
(b) семантический RAG без графа, (c) графовый обход без правил и LLM — на одном и том же
синтетическом корпусе с эталонной разметкой.

**H2.** Формальные правила обеспечивают точность обнаружения противоречий выше, чем LLM-анализ
пар фрагментов, а их объединение повышает полноту без существенной потери точности.

**H3.** Обязательная привязка к источникам (citation guard) снижает долю неподтверждённых
утверждений ассистента до ≈0 при умеренной потере полноты ответа.

**Методы сравнения** (одинаковые входы — набор документов и формулировка изменения):

| Метод | Как определяет «затронутое» |
|-------|-----------------------------|
| M1 Keyword | BM25 по тексту изменения → фрагменты top-k → упомянутые в них компоненты/документы |
| M2 RAG | эмбеддинги + BM25 (RRF) → top-k → компоненты/документы; с LLM — LLM выбирает из контекста |
| M3 Graph | извлечённый граф, BFS от требования без весов, правил и классов |
| M4 Hybrid | предлагаемый метод (раздел 6.3) |

**Метрики:** P/R/F1 по затронутым компонентам и документам (микро- и макроусреднение по
сценариям), полнота цепочек зависимостей (доля эталонных путей, восстановленных системой), P/R/F1
извлечения требований (сравнение с эталоном по (субъект, параметр, оператор, значение)), P/R/F1
противоречий по типам, время, доля утверждений с валидной ссылкой.

**Абляции:** без весов; без правил физической природы параметра; без формальной перепроверки;
глубина 1…5; шум в документах (скан/опечатки) → деградация извлечения → деградация анализа.

**Масштабируемость:** синтетическое увеличение графа (×10, ×100 компонентов) — время построения и анализа.

**Правило честности:** в `experiments/results/` попадают только реальные прогоны с хешем
датасета, коммитом и параметрами. Чего не измерили — помечаем как гипотезу.

## 8. Что откладываем

| Функция | Почему можно отложить |
|---------|-----------------------|
| Адаптер Neo4j | Интерфейс `GraphStore` есть, реализация не влияет на научный результат |
| CAD/чертежи (DWG, STEP) | Только точка расширения (интерфейс парсера) |
| Полноценная аутентификация (SSO, LDAP) | В MVP — локальные пользователи, роли viewer/engineer/admin, токен |
| Мультитенантность в полном объёме | Изоляция на уровне `project_id` во всех таблицах и запросах |
| Извлечение координат из DOCX | В DOCX нет страниц — храним номер абзаца/таблицы |
| Внешние LLM API | Интерфейс есть, по умолчанию выключено |
| Асинхронная очередь обработки | Документы небольшие; синхронная обработка + статусы |

## 10. Обзор аналогов — статус

Обзор (Teamcenter, 3DEXPERIENCE, Windchill, Aras, отечественные PLM, RAG-платформы,
публикации по KG+LLM в инженерии) выполняется на этапе 6 с источниками. До него формулировки
научной новизны считаются **предварительными**.
